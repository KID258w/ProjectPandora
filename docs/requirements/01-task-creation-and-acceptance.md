# 需求 01：任务创建、分配与验收链

## 文档信息

- 当前版本：`v0.9`
- 当前状态：MVP 实现需求基线，团队已确认并纳入实现范围；本版暂不纳入的能力见第 15 节
- 所属阶段：Sprint 0——需求分析与产品设计
- 当前已整理范围：普通员工、团队长、部门经理和创始人的任务链，以及部门经理之间的跨部门协作请求
- 待进一步细化的边界：本版 MVP 范围内的任务链与跨部门协作规则已确认；延期申请、已完成任务重开、跨部门请求接受后取消等不纳入本版 MVP

## 1. 需求目标

建立一条从上级创建并分配任务，到执行人推进任务、提交成果，再由直接上级验收的完整业务链。

跨部门支援不允许部门经理直接给其他部门员工派任务，而由部门经理向目标部门经理发起协作请求；目标部门接受后，在本部门内创建或承接工作并按原有层级分配，最终由请求发起部门验收协作结果。

当前确定的基本层级为：

```text
创始人
  ↓ 创建并分配任务
部门经理
  ↓ 分配或拆分任务
  团队长
  ↓ 分配或拆分任务
普通员工
  ↓ 执行并提交任务
团队长验收
```

普通员工是任务执行者，不具备创建任务或向他人分配任务的权限。团队长既可以执行本人负责的工作，也可以创建团队独立任务、拆分任务、向下属分配任务并验收员工提交的成果。

## 2. 普通员工的权限边界

| 操作 | 是否允许 | 说明 |
| --- | --- | --- |
| 创建任务 | 否 | 普通员工不能独立创建业务任务 |
| 分配任务 | 否 | 普通员工不能向其他成员派发任务 |
| 接收任务 | 自动接收 | 团队长分配后，任务自动进入员工的“我的任务” |
| 拒绝任务 | MVP 不支持 | 对任务存在疑问时，通过进展说明或线下沟通反馈 |
| 开始任务 | 是 | 员工主动开始任务后，任务进入“进行中” |
| 更新任务进度 | 是 | 员工可以更新进度百分比并填写进展说明 |
| 提交完成 | 是 | 员工填写完成说明后，将任务提交给团队长验收 |
| 验收任务 | 否 | 任务由直接派发任务的团队长验收 |
| 修改任务定义 | 否 | 不能修改任务标题、负责人、完成标准和截止时间等信息 |
| 查看他人任务 | 否 | 只能查看分配给自己的任务及其必要的上级任务背景 |

## 3. 普通员工任务主流程

```text
团队长分配任务
      ↓
任务自动进入“我的任务”
状态：待开始
      ↓
员工查看任务并点击“开始任务”
状态：进行中
      ↓
员工根据实际情况更新任务进度和进展说明
      ↓
员工填写完成说明并提交任务
状态：待验收，进度：100%
      ↓
团队长验收
   ┌──┴──────────┐
   ↓             ↓
验收通过        验收不通过
状态：已完成    状态：需修改
                  ↓
              员工查看退回原因
                  ↓
              继续处理并重新提交
```

## 4. 任务状态与转换规则

普通员工任务的核心状态为：

```text
待开始 → 进行中 → 待验收 → 已完成
                    ↓
                  需修改
                    ↓
                  进行中
```

| 当前状态 | 触发操作 | 下一状态 | 操作者 |
| --- | --- | --- | --- |
| 待开始 | 开始任务 | 进行中 | 普通员工 |
| 待开始 | 首次进入任务详情 | 进行中 | 接收上级任务的团队长或部门经理 |
| 进行中 | 提交完成 | 待验收 | 普通员工 |
| 待验收 | 验收通过 | 已完成 | 团队长 |
| 待验收 | 退回修改 | 需修改 | 团队长 |
| 需修改 | 继续处理 | 进行中 | 普通员工 |
| 进行中 | 再次提交 | 待验收 | 普通员工 |
| 待开始、进行中、待验收、需修改 | 直接派发者填写原因并取消 | 已取消 | 直接派发者 |
| 尚未完成的后代任务 | 父任务被取消 | 已取消 | 系统级联 |

任务取消与级联规则如下：

- 只有任务的直接派发者可以主动取消该任务；任务创建者仅在其同时是直接派发者时拥有该权限。普通执行人不能直接取消上级派发给自己的任务。
- 直接派发者取消任务时必须填写取消原因。“待开始、进行中、待验收、需修改”状态的任务均可取消；“已完成”任务不可取消。
- 被取消任务存在子任务时，系统将所有尚未完成的后代任务级联标记为“已取消”；后代任务若已完成，则保留“已完成”状态。已经取消的后代保留原取消记录。
- 子任务被单独取消时，取消只向下影响该子任务尚未完成的后代，不向上取消父任务，也不影响兄弟任务；父任务状态保持不变，后续安排由父任务负责人另行处理。
- 级联是直接派发者取消父任务后由系统执行的状态联动，不代表该派发者获得逐条查看或手动操作所有下级任务的权限；只影响该任务树，不影响同级或其他任务。
- 级联取消的后代记录取消来源，并继承父任务的取消原因；系统保留各级任务、进度、提交内容、日志关联和历史记录，不物理删除任务。
- 父任务或后代任务被取消后，相关执行人和管理者收到 App 内红点提醒；被取消任务不可再更新进度、提交或验收。
- 已取消任务不出现在当前任务列表和首页任务榜单中，但可在历史记录中查看；个人十大重点工作中的已取消任务应移除。
- 本规则适用于正式任务树，不自动改变独立的跨部门协作请求状态；跨部门请求按第 13.2 节的单独规则处理。

补充规则：

- “逾期”是任务的附加标记，不替代任务的业务状态。
- 已逾期任务仍然可以更新进度和提交验收。
- 已完成任务只读，保留完整的执行与验收记录；MVP 不支持重新打开任何已完成任务。后续需要继续处理时，应创建新的后续任务。
- 已取消任务保留历史并只读；已完成任务不能取消或重新变为进行中。

### 4.1 关键操作提醒

MVP 通过 App 内红点提醒用户处理新的任务或流程结果：

- 新任务派发给执行人时，执行人收到提醒。
- 执行人提交验收、直接上级验收通过或退回修改时，相关处理人收到提醒。
- 跨部门协作请求送达、被接受、被拒绝或被发起方撤回，以及协作结果提交待验收或被退回补充时，相关部门经理收到提醒。
- 任务定义发生修改并影响执行人时，执行人收到提醒。
- 任务被取消或因父任务取消而级联取消时，相关执行人和管理者收到提醒；提醒中应能查看取消原因和触发取消的上级任务。
- 用户查看对应任务或协作请求后，清除该条未读提醒。

Android 系统通知可在开发阶段结合技术方案作为增强能力；MVP 验收以 App 内红点提醒为准。

## 5. “我的任务”界面

普通员工只需要一个任务管理主面板：`我的任务`。

任务列表可以按照以下状态筛选：

- 待开始
- 进行中
- 需修改
- 待验收
- 已完成
- 已取消（历史记录）

不同状态允许的操作如下：

| 任务状态 | 普通员工可执行的操作 |
| --- | --- |
| 待开始 | 查看详情、开始任务 |
| 进行中 | 查看详情、更新进度、提交完成 |
| 需修改 | 查看退回原因、继续处理、更新进度、重新提交 |
| 待验收 | 查看任务及本次提交内容 |
| 已完成 | 查看任务、进度历史和验收结果 |
| 已取消 | 仅从历史记录查看取消原因和保留的任务历史 |

已取消任务不出现在默认的当前任务列表中。

## 6. 任务详情

普通员工查看任务时，至少应当看到：

- 任务标题
- 任务说明
- 完成标准
- 派发人
- 所属上级任务名称（如存在）
- 优先级
- 开始时间
- 截止时间
- 当前状态
- 当前进度
- 相关附件
- 历史进度记录
- 已关联的工作日志
- 验收结果或退回原因

普通员工只能了解所属上级任务的必要背景，不能查看同一上级任务下其他员工的任务明细。

创建或编辑任务时，以下字段为必填：任务标题、任务说明、明确的责任人、截止时间、完成/验收标准。优先级和附件为选填项。多人共同完成的工作应拆分为多个责任人明确、可独立验收的子任务。

任务创建者或直接派发者可以修改自己创建或派发的任务定义，包括标题、说明、责任人、截止时间和完成/验收标准；修改可在任务开始后进行。任务处于“待验收”时暂不允许修改定义，需先由验收者验收或退回；“已完成”任务只读。每次修改保留操作人、时间和修改内容，并提醒受影响的执行人。普通员工不能修改任务定义。MVP 不提供单独的延期申请流程；执行人通过进度说明反馈延期风险，由直接派发者按上述规则修改截止时间。

## 7. 任务进度更新

员工可以在任务处于“进行中”或“需修改”状态时更新进度，单次更新至少包含：

- 当前进度百分比
- 本次进展说明
- 更新时间
- 更新人

必要时可以附加成果文件或图片。每次进度更新均应独立保存，不覆盖历史记录。

示例：

```text
9 月 20 日  20%  完成需求确认
9 月 21 日  40%  完成接口结构设计
9 月 22 日  60%  完成登录接口开发
```

任务进度百分比由员工根据实际完成情况填写，不根据日志数量自动计算。

## 8. 每日日志与任务的关系

任务进度与每日日志是两类独立但可以关联的数据：

- 任务进度回答“这项任务目前完成到什么程度”。
- 每日日志回答“员工今天具体做了什么”。

日志在独立的“今日日志”界面填写。任务与日志的关联关系仅在新增或编辑日志时建立，任务页面不提供新增或修改日志关联的入口。

```text
进入“今日日志”
      ↓
填写当天工作内容
      ↓
选择本篇日志关联的任务
      ↓
保存日志
      ↓
系统在对应任务详情中只读展示该日志
```

关联规则：

- 一篇日志可以关联多个任务。
- 一个任务可以关联多篇不同日期的日志。
- 日志可以不关联任何任务，例如培训、会议等非任务型工作。
- 填写日志时不强制更新任务进度。
- 更新任务进度时不强制填写日志。
- 提交任务完成时，已关联日志可作为验收参考，但 MVP 暂不要求任务必须具有关联日志。

## 9. 提交完成与验收

普通员工不能通过单击按钮直接把任务变为“已完成”。员工提交任务时，至少需要填写：

- 完成说明
- 最终交付结果或成果位置
- 附件为选填项

提交成功后：

- 任务进度更新为 `100%`。
- 任务状态变为“待验收”。
- 员工等待团队长处理，不能继续更新该任务。

团队长验收通过后，任务进入“已完成”；验收不通过时，团队长必须填写退回原因，任务进入“需修改”。员工查看原因、继续处理后可以重新提交。

任务提交后进入“待验收”，执行人不能自行撤回；如需补充或修正，由验收者退回并填写原因。

## 10. 团队长任务链

### 10.1 页面结构

团队长点击“任务”后，使用两个固定页面：

```text
任务
├─ 我的任务
│  ├─ 上级分配
│  └─ 团队独立
│
└─ 团队任务
```

两个页面的职责如下：

- `我的任务`：展示团队长本人负责或需要亲自执行的任务，并提供“创建任务”功能。
- `团队任务`：展示已有下属参与的任务，以及该任务的人员分配和完成情况。

“上级分配”和“团队独立”只是“我的任务”中的任务来源标签，不单独建立新的页面：

- `上级分配`：部门经理分配给团队长的任务，以及从该任务中分配给团队长本人的子任务。
- `团队独立`：团队长主动创建的任务，以及从该任务中分配给团队长本人的子任务。

### 10.2 上级分配任务

部门经理向团队长分配任务后，根任务自动进入“我的任务—上级分配”。团队长可以选择独自完成，也可以继续进行任务分配。

#### 团队长独自完成

如果任务只由团队长本人负责：

- 根任务只在“我的任务—上级分配”中显示。
- 任务不在“团队任务”中显示。
- 团队长直接执行任务、更新整体进度并向部门经理提交验收。

#### 团队长向下属分配

只要任务被分配给至少一名下属：

- 根任务继续保留在“我的任务—上级分配”。
- 根任务同步显示到“团队任务”。
- “团队任务”展示根任务下的全部人员分配和完成情况。
- 每名具体执行人对应一条独立子任务。

示例：

```text
我的任务
└─ [上级分配] 完成移动端开发

团队任务
└─ 完成移动端开发
   ├─ 员工甲：登录页面
   └─ 员工乙：日志页面
```

如果团队长本人也参与具体分工，则为团队长创建一条独立的本人子任务：

```text
团队任务
└─ 完成移动端开发
   ├─ 员工甲：登录页面
   ├─ 员工乙：日志页面
   └─ 团队长：模块集成

我的任务
├─ [上级分配] 完成移动端开发
└─ [上级分配] 模块集成
   所属任务：完成移动端开发
```

根任务与团队长本人的子任务是两条不同记录：根任务表示团队长承担的整体责任，本人子任务表示团队长亲自执行的具体工作。

### 10.3 团队独立任务

团队长可以在“我的任务”页面创建任务。由团队长主动创建的根任务归入“我的任务—团队独立”。

#### 只有团队长本人负责

如果团队长创建任务后只由本人负责：

- 根任务只在“我的任务—团队独立”中显示。
- 不需要执行任务分配。
- 不在“团队任务”中显示。
- 团队长直接处理并完成该任务。

#### 分配给一名或多名下属

如果团队长把任务分配给一名下属，或者拆分给多名下属：

- 根任务继续保留在“我的任务—团队独立”。
- 根任务同步显示到“团队任务”。
- “团队任务”展示所有子任务、负责人和完成情况。

即使任务只分配给一名下属，只要有下属参与，也必须在“团队任务”中显示。

#### 团队长与下属共同参与

如果多人任务中包含团队长本人：

- “团队任务”展示包括团队长在内的完整分配情况。
- 系统同时在“我的任务—团队独立”中新增团队长本人的子任务。
- 本人子任务显示所属根任务，避免与根任务混淆。

示例：

```text
团队任务
└─ 完成本周版本发布
   ├─ 员工甲：功能测试
   ├─ 员工乙：缺陷修复
   └─ 团队长：版本合并

我的任务
├─ [团队独立] 完成本周版本发布
└─ [团队独立] 版本合并
   所属任务：完成本周版本发布
```

### 10.4 页面同步规则

| 根任务来源 | 参与人员 | “我的任务”显示 | “团队任务”显示 |
| --- | --- | --- | --- |
| 上级分配 | 只有团队长 | 根任务 | 不显示 |
| 上级分配 | 包含下属，团队长不承担具体子任务 | 根任务 | 根任务及下属分配详情 |
| 上级分配 | 下属与团队长共同参与 | 根任务和团队长本人子任务 | 完整分配详情，包括团队长 |
| 团队独立 | 只有团队长 | 根任务 | 不显示 |
| 团队独立 | 包含下属，团队长不承担具体子任务 | 根任务 | 根任务及下属分配详情 |
| 团队独立 | 下属与团队长共同参与 | 根任务和团队长本人子任务 | 完整分配详情，包括团队长 |

可以将上述规则概括为：

```text
只有团队长本人负责
→ 只显示在“我的任务”

只要有下属参与
→ 根任务同步显示到“团队任务”

团队长也被分配了具体子任务
→ 在“我的任务”中新增本人子任务
```

“同步显示”表示两个页面从不同角度读取同一组根任务和子任务数据，不得复制创建两份根任务记录。

### 10.5 团队长本人子任务

团队长本人子任务遵循以下规则：

- 本人子任务继承根任务的来源标签。
- 本人子任务必须显示所属根任务。
- 本人子任务不要求填写进度百分比，只需要“未完成”和“已完成”等完成状态。
- 团队长完成本人子任务后直接标记完成，不进行自我验收。
- 本人子任务的完成情况在“团队任务”的分配详情中同步更新。

如果上级分配的任务完全由团队长本人承担，则不额外创建本人子任务，团队长直接处理根任务。

### 10.6 团队任务进度

员工负责更新各自子任务的进度，系统在“团队任务”中展示客观的子任务状态，例如：

```text
子任务共 5 项
已完成 2 项｜待验收 1 项｜进行中 1 项｜待开始 1 项
```

根任务进度不根据子任务百分比自动加权计算，由团队长结合实际交付情况手动更新。子任务数量和状态只作为团队长判断根任务整体进度的参考。

### 10.7 团队长验收员工任务

员工提交子任务后，任务进入“待验收”。团队长可以在“团队任务”中查看提交内容并进行处理：

```text
员工提交子任务
      ↓
团队长查看完成说明、成果和相关日志
      ↓
   ┌──┴──────────┐
   ↓             ↓
验收通过        退回修改
状态：已完成    状态：需修改
                  ↓
              员工修改并重新提交
```

团队长退回任务时必须填写原因。团队长不能代替员工修改进度或完成说明。

### 10.8 根任务结束或向上提交

当根任务包含子任务时，团队长只有在满足以下条件后，才能结束根任务或将其向上提交：

- 所有必须完成的员工子任务均已验收通过。
- 团队长本人的子任务均已标记完成。
- 不存在“待验收”或“需修改”的必要子任务。
- 团队长已填写根任务的整体完成说明。

根据根任务来源执行不同的后续操作：

- `上级分配`：团队长向部门经理提交根任务，由部门经理进行验收。
- `团队独立`：团队长完成下属验收和整体汇总后，结束根任务，不再进行自我验收。

## 11. 部门经理任务链

### 11.1 角色定位与权限边界

部门经理是创始人的直属下级，同时承担工作执行和部门管理职责。部门经理可以接收创始人派发的任务，也可以根据公司目标、会议结果和部门工作自主创建部门任务；其下游仍然是团队长。

部门经理遵守以下权限边界：

- 可以接收创始人直接派发的任务。
- 可以向本部门的团队长分配任务。
- 不能绕过团队长直接向普通员工分配任务。
- 在任务界面中，只查看本人负责的任务，以及本人直接派发给团队长的任务和直接验收所需信息。
- 不在任务界面向下展开查看团队长继续拆分给普通员工的任务明细；下属的工作视图和已提交日志通过视图、日志模块按权限筛选查看，详见需求 03、04。
- 只能验收直属团队长提交的任务，不能直接验收普通员工任务。
- 不能查看或管理其他部门的任务。
- 创始人是部门经理的直接上级，也是当前职级体系中的最高一级。
- 创始人可以在视图和日志模块筛选查看公司范围成员的工作视图及已提交日志，并可以向部门经理派发任务；任务派发界面不因此提供跨层级的员工任务明细透视。
- 创始人向部门经理派发任务属于业务任务分配；当前规则仅确认其可分配给部门经理，不能据此推定创始人可以绕过部门经理直接向团队长或普通员工派发。
- 创始人作为直接派发者，负责验收自己派发给部门经理的任务，也可按本节规则取消自己派发的任务并触发未完成后代的级联取消。

### 11.2 页面结构

部门经理点击“任务”后，可使用两个任务列表和一个跨部门协作入口：

```text
任务
├─ 我的任务
│  ├─ 上级分配
│  ├─ 部门自主
│  └─ 跨部门工作
├─ 我派发的
└─ 跨部门协作
   ├─ 我发起的
   └─ 待我处理
```

各入口职责如下：

- `我的任务`：展示创始人派发给部门经理的任务、部门经理自主创建并整体负责的根任务，以及多人分工时分配给部门经理本人的子任务；页面提供“创建任务”功能。
- `我派发的`：仅展示部门经理本人向团队长分配的任务及直接验收所需的完成情况，不汇总展示团队长自主创建或继续拆分给员工的任务。
- `跨部门协作—我发起的`：展示部门经理向其他部门经理发送的协作请求及其处理状态。
- `跨部门协作—待我处理`：展示其他部门经理发给当前部门的协作请求；接受后，该项工作进入“我的任务—跨部门工作”。

“我的任务”按来源分为“上级分配”“部门自主”和“跨部门工作”：

- `上级分配`：创始人派发给部门经理的任务，以及从该任务中分配给部门经理本人的子任务。
- `部门自主`：部门经理自己创建的部门根任务，以及从该任务中分配给部门经理本人的子任务。
- `跨部门工作`：其他部门经理发起并由当前部门经理接受的协作工作，以及从该工作中分配给当前部门经理本人的子任务。

三个来源标签下均可按“待开始、进行中、待验收、需修改、已完成”等任务状态筛选；跨部门协作请求尚未被接受时不进入任务状态列表。

根任务与本人子任务通过任务结构区分：

- 部门经理的根任务显示本部门范围内的整体进度和直接分配概况，不展示其他部门的子任务明细。
- 本人子任务显示“所属任务”，表明这是部门经理亲自执行的具体工作。

创始人派发给部门经理的任务归入“我的任务—上级分配”；部门经理自主创建并负责的任务归入“我的任务—部门自主”；接受的跨部门工作归入“我的任务—跨部门工作”。

### 11.3 部门经理独自完成任务

部门经理在“我的任务—部门自主”中创建任务后，如果任务只由本人负责：

- 根任务只在“我的任务”中显示。
- 任务不在“我派发的”中显示。
- 不需要创建额外的本人子任务。
- 部门经理直接处理并完成根任务。
- 任务不需要创始人验收。

示例：

```text
我的任务
└─ 编写部门年度规划
```

### 11.4 向团队长分配任务

只要有至少一名团队长参与，部门经理负责的根任务就同步显示到“我派发的”。

```text
我的任务
└─ 完成 Pandora 第一阶段交付

我派发的
└─ 完成 Pandora 第一阶段交付
   ├─ 移动端团队长：完成移动端
   ├─ 后端团队长：完成后端服务
   └─ 测试团队长：完成系统测试
```

分配规则如下：

- 根任务继续保留在部门经理的“我的任务”。
- 每名具体负责的团队长对应一条独立子任务。
- 团队长子任务进入对应团队长的“我的任务—上级分配”。
- 团队长可以独自完成该任务，也可以继续向本团队普通员工拆分和分配。
- 部门经理不能在负责人选择中直接选择普通员工。

“同步显示”表示“我的任务”和“我派发的”从不同角度读取同一组任务数据，不得复制创建两份根任务记录。

### 11.5 部门经理本人参与任务

如果部门经理在分配部门任务时也承担具体工作，则为部门经理创建一条独立的本人子任务：

```text
我派发的
└─ 完成 Pandora 第一阶段交付
   ├─ 移动端团队长：完成移动端
   ├─ 后端团队长：完成后端服务
   └─ 部门经理：完成最终汇报

我的任务
├─ 完成 Pandora 第一阶段交付
└─ 完成最终汇报
   所属任务：完成 Pandora 第一阶段交付
```

部门经理本人子任务遵循以下规则：

- 必须显示所属根任务。
- 不要求填写进度百分比，只需要“未完成”和“已完成”等完成状态。
- 完成后由部门经理直接标记完成，不进行自我验收。
- 完成情况在“我派发的”对应任务详情中同步更新。

### 11.6 任务界面的查看范围

部门经理的任务界面围绕本人负责和本人直接派发的任务组织，不提供对本部门任务树的任意向下穿透：

- “我的任务”展示创始人派发给部门经理的任务、部门经理自主创建并负责的根任务，以及本人承担的具体子任务。
- “我派发的”只展示部门经理直接派发给团队长的任务及其直接负责人、状态、进度和提交验收内容。
- 团队长继续拆分给普通员工的子任务，不在部门经理的任务列表或任务详情中展开。
- 团队长自主创建、且没有分配给部门经理的团队独立任务，不进入部门经理的任务列表。
- 部门经理不能在任务界面直接查看或手动修改、重新分配、取消、验收、退回普通员工的个人任务。若部门经理直接派发的上级任务被取消，系统仍按本节规则自动级联更新其未完成后代的状态。

部门经理如需了解团队长或普通员工的工作视图、日志，应通过月/周/日视图和日志模块的下属筛选入口查看；这些入口默认显示本人，筛选范围受组织权限限制，详见需求 03、04。

### 11.7 团队自主任务的任务界面范围

团队长自主创建的任务由团队长负责分配、跟进、验收和结束，不列入部门经理的“我派发的”。部门经理不通过任务界面展开这类任务及其员工子任务；需要了解下属整体工作时，使用视图和日志模块的筛选功能。

### 11.8 部门任务进度

部门经理只维护自己负责的根任务进度，并在“我派发的”中跟进直接派发给团队长的任务状态和提交结果。系统不根据子任务进度自动计算根任务进度；部门经理结合团队长的直接反馈和实际交付情况手动更新整体进度。员工级任务进度不在部门经理任务界面中汇总展示。

### 11.9 部门经理验收团队长任务

团队长只有在员工必要子任务均已验收通过、团队长本人子任务均已完成，并填写整体完成说明后，才能向部门经理提交任务。

```text
团队长提交任务
      ↓
部门经理查看团队整体完成说明和成果
      ↓
   ┌──┴──────────┐
   ↓             ↓
验收通过        退回修改
状态：已完成    状态：需修改
                  ↓
              团队长组织修改并重新提交
```

部门经理退回团队长任务时必须填写原因。部门经理只能对自己直接派发、由团队长提交验收的任务执行验收操作；员工任务仍由对应团队长验收，部门经理不通过任务验收界面下钻查看员工任务明细。

### 11.10 结束部门根任务

部门经理只有在自己直接派发给团队长的必要任务均已验收通过、本人子任务均已标记完成，并填写部门根任务的整体完成说明后，才能结束或向创始人提交部门根任务。部门经理无需在任务界面检查团队长继续拆分给员工的明细；具体员工任务由团队长负责验收。

部门经理自主创建的部门根任务，在所有必要子任务完成并汇总后，由部门经理结束。

如果部门经理负责的任务是创始人公司级根任务下的部门子任务，部门经理完成本部门分配和汇总后，向创始人提交该部门子任务，由创始人作为直接派发者验收；公司级根任务仍由创始人负责，部门经理不能自行结束。

### 11.11 完整层级任务链

```text
创始人创建并向部门经理派发任务
        ↓
部门经理接收任务并进行统筹
        ↓
部门经理创建并分配团队任务
        ↓
任务进入团队长“我的任务—上级分配”
        ↓
团队长独自完成，或继续拆分给普通员工
        ↓
普通员工执行并提交任务
        ↓
团队长验收员工任务
        ↓
团队长汇总并向部门经理提交任务
        ↓
部门经理验收团队长任务
        ↓
部门经理汇总并向创始人提交其派发的任务
        ↓
创始人验收直接派发给部门经理的任务
```

## 12. 创始人任务链

### 12.1 角色定位与页面结构

创始人是当前业务职级体系的最高一级，是部门经理的直接上级。创始人可以在移动端创建公司级任务并派发给一个或多个部门经理，但不能绕过部门经理直接向团队长或普通员工派发任务。创始人不承担管理员式的员工资料维护权限。

创始人的“任务”界面包括：

```text
任务
├─ 我的任务
└─ 我派发的
```

- `我的任务`是创始人创建任务的入口，也展示创始人本人负责的根任务和分配给自己的子任务。
- `我派发的`只跟进创始人直接派给部门经理的任务及其提交验收内容，不展开查看部门经理继续分配给团队长或员工的任务树。
- 创始人只能从“我的任务”创建任务并向下派发；“我派发的”不提供独立创建任务的入口。
- 创始人查看下属工作视图和已提交日志时，使用视图、日志模块的人员筛选；任务派发界面不承担跨层级透视，详见需求 03、04。

### 12.2 创建公司级根任务并分配给多个部门

创始人只能从“我的任务”创建任务。只由创始人本人负责的任务保留在“我的任务”；需要多个部门协作时，保留一个共同根任务，并为每位参与的部门经理建立独立的部门子任务：

```text
我的任务
└─ [公司级根任务] 上线新产品

我派发的
└─ 上线新产品
   ├─ 部门经理甲：完成市场宣传方案
   └─ 部门经理乙：完成产品开发
```

规则如下：

- 公司级根任务保留在创始人的“我的任务”。
- 每位部门经理获得一条独立、范围明确的子任务，并作为该子任务的直接负责人。
- 部门经理收到的部门子任务进入其“我的任务—上级分配”，作为本部门后续拆分和执行的起点。
- 部门经理只查看和管理分配给本部门的子任务及必要的根任务背景，不查看其他部门的任务分配明细。
- 各部门经理在本部门内继续按“部门经理 → 团队长 → 普通员工”的层级拆分，不得跨部门派发。
- “我派发的”与“我的任务”读取同一根任务及其部门子任务数据，不重复创建根任务记录。
- 创始人根任务的整体进度由创始人结合交付情况手动维护，不按部门子任务进度自动加权计算。
- 所有必要部门子任务均已由创始人验收、创始人本人子任务均已完成后，创始人填写整体完成说明并手动结束公司级根任务。

### 12.3 创始人参与根任务

如果创始人将公司级任务拆分给多个部门，同时也承担一部分具体工作，则为创始人本人建立独立子任务：

```text
我的任务
├─ [公司级根任务] 上线新产品
└─ [本人子任务] 完成发布会致辞
   所属任务：上线新产品

我派发的
└─ 上线新产品
   ├─ 部门经理甲：完成市场宣传方案
   └─ 部门经理乙：完成产品开发
```

创始人本人子任务在“我的任务”中显示所属根任务；完成后由创始人本人标记完成，不进行自我验收。根任务仍由创始人负责整体进度和收尾。

### 12.4 直接派发与验收

任务由直接派发者验收：

| 直接派发者 | 直接受派者 | 验收者 |
| --- | --- | --- |
| 创始人 | 部门经理 | 创始人 |
| 部门经理 | 团队长 | 部门经理 |
| 团队长 | 普通员工 | 团队长 |

创始人只验收自己直接派发给部门经理的子任务，不直接验收团队长或普通员工的任务。部门经理完成本部门工作并提交后，创始人验收对应的部门子任务；各部门子任务和创始人本人子任务的完成情况由创始人汇总，根任务进度不自动计算。

## 13. 跨部门协作请求

### 13.1 发起范围与职责

跨部门临时支援通过“协作请求”处理，不允许一个部门经理直接给其他部门员工派发任务。由发起部门的部门经理代表本部门向目标部门经理发送请求；普通员工和团队长在 MVP 中不直接发起跨部门请求。

```text
发起部门经理 A
      ↓ 发送协作请求
目标部门经理 B
      ↓ 接受后在本部门内拆分
团队长 → 普通员工
      ↓ 完成本部门交付
部门经理 B 提交协作结果
      ↓
部门经理 A 验收并关闭请求
```

协作请求表达的是“请求另一个部门承接并提供支持”，不是发起方对目标部门的任务派发。目标部门经理接受前，该请求不进入目标部门的“我的任务”。

### 13.2 跨部门协作界面

部门经理的任务模块提供“跨部门协作”入口，分别展示：

```text
跨部门协作
├─ 我发起的
└─ 待我处理
```

- 发起部门经理在“我发起的”查看请求对象、请求内容和处理状态。
- 目标部门经理在“待我处理”查看发给本部门的请求，并执行接受或拒绝操作。
- 请求至少应说明协作事项和预期交付，以便双方理解工作范围，并供发起方后续验收。
- 请求尚未被接受时，仅作为协作请求展示，不作为目标部门的正式任务。
- 正常状态依次为“待对方接受 → 办理中 → 待发起方验收 → 已关闭”；目标部门拒绝时进入“已拒绝”，发起方在目标部门接受前撤回时进入“已撤回”。

拒绝规则如下：

- 目标部门经理拒绝请求时必须填写理由；未填写理由时不能提交拒绝操作。MVP 使用必填文本说明，可提供常见原因提示，但不要求另建复杂原因分类。
- 请求被拒绝后，不进入目标部门经理的“我的任务—跨部门工作”；原请求保留为“已拒绝”，发起方可以查看拒绝理由。
- 发起方如仍需协作，可根据拒绝理由调整内容后重新发起一条新请求；原请求及其拒绝记录保留，不重新打开。
- 信息不完整时也通过“拒绝并说明信息不完整”处理；MVP 不另设“要求补充信息”状态。

请求修改与撤回规则如下：

- 请求发出后，发起方不能直接编辑已发送的请求；目标部门尚未接受时，发起方可以填写撤回原因并撤回。未填写原因时系统阻止撤回。
- 撤回后原请求保留为“已撤回”；如仍需协作，发起方调整内容后创建一条新请求。
- 目标部门接受后，MVP 不提供撤回或取消该跨部门协作请求的操作，请求内容也不能直接修改；目标部门按已接受的范围继续处理。新增协作范围须另建请求，原请求仍按原目标办理。
- 创始人不查看、不接受、不拒绝、不验收或协调跨部门协作请求；请求仅对发起部门经理 A 和目标部门经理 B 可见。

跨部门请求字段规则如下：

- 请求事项说明和预期交付为必填。
- 期望完成时间、发起部门现有任务关联和附件均为选填。
- MVP 不设置跨部门请求优先级字段。

### 13.3 接受请求后的部门内任务

目标部门经理在跨部门协作界面接受请求后：

- 系统将该协作工作显示在目标部门经理“我的任务—跨部门工作”中。
- 目标部门经理成为该项工作的负责人，可以像处理其他任务一样自行执行，或创建子任务并分配给本部门团队长。
- 目标部门经理参与具体执行时，按已有规则在“我的任务”中保留本人子任务。
- 由目标部门经理创建并派发给团队长的子任务同步出现在其“我派发的”中，并由部门经理按本部门任务链验收。
- 发起部门经理只能查看协作请求及目标部门经理提交的协作结果，不查看目标部门的团队长和员工任务明细。

### 13.4 协作结果验收

目标部门完成内部任务后，由目标部门经理向请求发起方提交协作结果。发起部门经理 A 验收的是双方约定的协作结果，而不是目标部门员工的具体任务：

```text
目标部门经理 B 完成本部门分配与验收
              ↓
B 汇总并提交协作结果
              ↓
发起部门经理 A 验收协作结果
              ↓ 满足请求目标
          A 关闭协作请求
```

A 关闭请求即表示协作结果验收通过。若协作结果不满足请求目标，A 可以将结果退回 B 补充或修改：

- A 退回时必须填写原因；未填写原因时系统阻止退回操作。
- 退回后请求回到“办理中”，B 可以查看退回原因，在目标部门内补充或修改后重新提交；重新提交后请求回到“待发起方验收”。
- 退回不会关闭请求；A 收到重新提交提醒后再次验收，直至验收通过并关闭请求，或继续退回并说明原因。

## 14. 初步验收场景

### 场景 1：员工开始执行任务

- **假如** 团队长已经向员工分配一项处于“待开始”状态的任务
- **当** 员工点击“开始任务”
- **那么** 任务状态变为“进行中”，并记录实际开始时间

### 场景 2：员工更新任务进度

- **假如** 员工的任务处于“进行中”状态
- **当** 员工填写合法的进度百分比和进展说明并提交
- **那么** 系统保存新的进度记录，同时保留此前的历史记录

### 场景 3：员工提交任务完成

- **假如** 员工的任务处于“进行中”状态
- **当** 员工填写完成说明并提交任务
- **那么** 任务进度变为 `100%`，任务状态变为“待验收”

### 场景 4：缺少完成说明

- **假如** 员工准备提交任务完成
- **当** 员工未填写完成说明
- **那么** 系统拒绝提交，并提示员工补充必填内容

### 场景 5：任务验收不通过

- **假如** 员工提交的任务处于“待验收”状态
- **当** 团队长填写退回原因并选择“退回修改”
- **那么** 任务状态变为“需修改”，员工可以查看原因并继续处理

### 场景 6：员工在日志中关联任务

- **假如** 员工正在新增或编辑每日日志
- **当** 员工选择一个或多个自己的任务并保存日志
- **那么** 日志与所选任务建立关联，并在相应任务详情中只读展示

### 场景 7：员工尝试越权操作

- **假如** 当前用户是普通员工
- **当** 该用户尝试创建任务、向他人分配任务或修改任务定义
- **那么** 系统拒绝操作，并且不产生任何任务数据变更

### 场景 8：团队长独自执行上级分配任务

- **假如** 部门经理向团队长分配了一项任务，且团队长未向任何下属进行分配
- **当** 团队长查看任务列表
- **那么** 该任务只显示在“我的任务—上级分配”，不显示在“团队任务”

### 场景 9：团队长向一名下属分配任务

- **假如** 团队长负责一项根任务
- **当** 团队长创建一条子任务并分配给一名下属
- **那么** 根任务继续显示在“我的任务”，同时在“团队任务”中显示根任务及该下属的分配详情

### 场景 10：团队长参与多人任务

- **假如** 团队长正在对一项根任务进行多人分配
- **当** 团队长将其中一项具体工作分配给自己
- **那么** 系统创建团队长本人子任务，在“我的任务”中显示该子任务，并在“团队任务”中同步显示完整分配情况

### 场景 11：团队长创建本人独立完成的团队任务

- **假如** 团队长在“我的任务”中创建一项团队独立任务
- **当** 该任务只由团队长本人负责且未分配给下属
- **那么** 任务只显示在“我的任务—团队独立”，不显示在“团队任务”

### 场景 12：团队长验收员工任务

- **假如** 员工提交的子任务处于“待验收”状态
- **当** 团队长确认成果符合完成标准并选择“验收通过”
- **那么** 员工子任务变为“已完成”，团队任务中的分配详情同步更新

### 场景 13：存在未完成子任务时提交根任务

- **假如** 根任务下仍存在“待验收”或“需修改”的必要子任务
- **当** 团队长尝试结束根任务或向部门经理提交验收
- **那么** 系统拒绝操作，并提示团队长先处理未完成的必要子任务

### 场景 14：创始人向部门经理派发任务

- **假如** 当前用户是创始人，目标用户是其直接下属部门经理
- **当** 创始人创建任务并将其分配给该部门经理
- **那么** 该任务进入部门经理“我的任务—上级分配”，并显示派发人和任务要求

### 场景 15：部门经理创建本人独立完成的任务

- **假如** 部门经理在“我的任务”中创建了一项任务
- **当** 该任务只由部门经理本人负责且未分配给团队长
- **那么** 任务只显示在“我的任务”，不显示在“我派发的”

### 场景 16：部门经理向团队长分配任务

- **假如** 部门经理负责一项部门根任务
- **当** 部门经理为一名或多名团队长创建并分配子任务
- **那么** 根任务继续显示在部门经理的“我的任务”，同时显示在“我派发的”，并且对应子任务进入团队长的“我的任务—上级分配”

### 场景 17：部门经理参与多人任务

- **假如** 部门经理正在对部门根任务进行多人分配
- **当** 部门经理将其中一项具体工作分配给自己
- **那么** 系统创建部门经理本人子任务，在“我的任务”中显示所属根任务，并在“我派发的”对应任务详情中同步显示

### 场景 18：部门经理在任务界面查看直接派发任务

- **假如** 部门经理已经向团队长派发任务，团队长又将其拆分给普通员工
- **当** 部门经理打开“我派发的”并查看该任务
- **那么** 系统展示部门经理直接派发给团队长的任务及团队长提交的状态和验收内容，不展开普通员工的子任务明细；下属视图和日志应通过对应模块的筛选入口查看

### 场景 19：部门经理尝试在任务界面越级访问或操作员工任务

- **假如** 当前用户是员工所属部门的部门经理
- **当** 该用户尝试从任务界面展开员工任务明细，或直接修改、重新分配、取消、验收、退回员工任务
- **那么** 系统不在任务界面提供员工任务明细或上述操作，且不产生任何员工任务数据变更；其视图和日志查看权限按需求 03、04 执行

### 场景 20：部门经理验收团队长任务

- **假如** 团队长已经完成必要工作并向部门经理提交任务
- **当** 部门经理确认整体成果符合完成标准并选择“验收通过”
- **那么** 团队长任务变为“已完成”，“我派发的”中的对应状态同步更新

### 场景 21：部门经理退回团队长任务

- **假如** 团队长提交的任务处于“待验收”状态
- **当** 部门经理填写退回原因并选择“退回修改”
- **那么** 团队长任务变为“需修改”，由团队长组织后续修改并重新提交

### 场景 22：存在未完成团队长任务时结束部门自主根任务

- **假如** 部门经理自主创建的部门根任务下仍存在“待验收”或“需修改”的必要团队长任务
- **当** 部门经理尝试结束该部门自主根任务
- **那么** 系统拒绝操作，并提示部门经理先完成团队长任务的验收处理

### 场景 23：团队长自主任务不混入部门经理的派发列表

- **假如** 本部门团队长创建了团队独立任务，且该任务不是部门经理直接派发的
- **当** 部门经理查看自己的“我派发的”
- **那么** 系统不将该团队自主任务列入部门经理的派发列表；部门经理如需了解下属工作，应通过视图或日志模块的筛选功能查看

### 场景 24：创始人向多个部门分配同一公司级工作

- **假如** 创始人需要多个部门共同完成一项公司级工作
- **当** 创始人在“我的任务”创建一个公司级根任务，并为不同部门经理建立各自的子任务
- **那么** 根任务保留在创始人的“我的任务”，每个部门经理只收到本部门子任务，创始人在“我派发的”分别跟进各部门子任务

### 场景 25：创始人参与公司级任务

- **假如** 创始人创建了一个需要多部门协作的根任务
- **当** 创始人把其中一项具体工作分配给自己
- **那么** 系统在创始人的“我的任务”中显示根任务和本人子任务；本人子任务完成后由创始人标记完成，不进行自我验收

### 场景 26：创始人验收直接派发给部门经理的任务

- **假如** 部门经理已经完成创始人直接派发给自己的部门子任务并提交结果
- **当** 创始人在“我派发的”中审核该提交
- **那么** 创始人可以验收通过并完成该子任务，或按任务验收规则退回；创始人不直接验收该部门内团队长或员工任务

### 场景 27：部门经理发起跨部门协作请求

- **假如** 部门经理 A 需要其他部门提供支持
- **当** A 在“跨部门协作”中向部门经理 B 发送请求
- **那么** 请求出现在 A 的“我发起的”和 B 的“待我处理”中，且在 B 接受前不进入 B 的“我的任务”

### 场景 28：目标部门接受协作请求

- **假如** 部门经理 B 收到部门经理 A 的跨部门协作请求
- **当** B 在“待我处理”中接受该请求
- **那么** 协作工作进入 B 的“我的任务—跨部门工作”，B 可以按本部门的正常任务链自行执行或分配给团队长

### 场景 29：接受后的跨部门工作向下分配

- **假如** 部门经理 B 已接受一项跨部门协作请求
- **当** B 将具体工作拆分并派发给本部门团队长
- **那么** 相关团队长子任务按正常的上级分配流程进入团队长任务列表，B 在“我派发的”跟进并验收团队长提交

### 场景 30：发起部门验收跨部门协作结果

- **假如** 部门经理 B 已完成内部任务并向部门经理 A 提交协作结果
- **当** A 验收该结果并确认满足请求目标
- **那么** A 关闭协作请求；A 验收的是双方约定的协作结果，而不是 B 部门员工的具体任务

### 场景 31：跨部门请求方尝试访问目标部门员工任务

- **假如** 部门经理 A 发起的协作请求已被部门经理 B 接受并正在执行
- **当** A 查看该请求
- **那么** A 可以查看请求状态和 B 提交的协作结果，但不能通过该请求查看或管理 B 部门的团队长、员工任务明细

### 场景 32：非部门经理尝试发起跨部门请求

- **假如** 当前用户是普通员工或团队长
- **当** 该用户尝试直接向其他部门经理发起跨部门协作请求
- **那么** 系统拒绝该请求，不创建跨部门协作记录

### 场景 33：部门经理或团队长首次查看上级派发任务

- **假如** 创始人或部门经理已向部门经理或团队长派发任务
- **当** 受派者首次进入该任务详情
- **那么** 任务先自动出现在其“我的任务”中并处于“待开始”，首次进入详情后转为“进行中”

### 场景 34：创建任务时校验必填字段

- **假如** 有权限的管理角色正在创建任务
- **当** 任务标题、任务说明、责任人、截止时间或完成/验收标准任一必填项为空
- **那么** 系统阻止提交并提示补全字段；优先级和附件为空不阻止创建

### 场景 35：派发者修改未完成任务定义

- **假如** 任务尚未完成且不处于“待验收”状态
- **当** 任务创建者或直接派发者修改任务定义并保存
- **那么** 系统保存修改人、时间和修改内容，并提醒受影响的执行人；普通员工不能执行该修改

### 场景 36：拒绝跨部门协作请求

- **假如** 目标部门经理收到待处理的跨部门协作请求
- **当** 该经理填写拒绝理由并确认拒绝
- **那么** 请求变为“已拒绝”，目标部门不创建对应的正式任务，发起方收到红点提醒并可查看拒绝理由；未填写理由时系统阻止拒绝

### 场景 37：根据拒绝理由重新发起跨部门请求

- **假如** 发起部门经理查看到一条“已拒绝”的协作请求及其拒绝理由
- **当** 发起方调整协作内容并重新发起
- **那么** 系统创建一条新的待处理请求，原请求继续保留为“已拒绝”

### 场景 38：关键任务操作的 App 内提醒

- **假如** 发生新任务派发、提交验收、验收通过或退回、任务取消或级联取消、跨部门请求接受、拒绝或撤回、协作结果提交或退回等关键操作
- **当** 相关用户尚未查看对应任务或请求
- **那么** 对应入口显示未读红点；用户查看对应记录后清除该条提醒

### 场景 39：直接派发者取消未完成任务

- **假如** 一项任务处于未完成状态，且当前用户是该任务的直接派发者
- **当** 当前用户填写取消原因并确认取消
- **那么** 该任务变为“已取消”，保留任务及执行历史，不再允许继续更新、提交或验收，相关人员收到提醒

### 场景 40：取消父任务时级联取消未完成后代

- **假如** 直接派发者取消了一项已有多级子任务的父任务
- **当** 系统处理该取消操作
- **那么** 该任务树内所有未完成后代变为“已取消”并继承取消原因，已完成后代保持“已完成”，任务树之外的任务不受影响

### 场景 41：非直接派发者尝试取消任务

- **假如** 当前用户不是目标任务的直接派发者
- **当** 当前用户尝试单独取消该任务
- **那么** 系统拒绝操作且不改变任务状态；若该任务因父任务被取消而级联变化，则按系统级联规则处理

### 场景 42：单独取消子任务不影响父任务

- **假如** 一项未完成子任务由其直接派发者取消，且该子任务有父任务或兄弟任务
- **当** 系统处理子任务取消及其未完成后代的级联取消
- **那么** 子任务及其未完成后代变为“已取消”，父任务和兄弟任务状态保持不变

### 场景 43：发起方退回跨部门协作结果

- **假如** 目标部门经理 B 已提交协作结果，协作请求处于“待发起方验收”
- **当** 发起部门经理 A 填写退回原因并选择退回
- **那么** 请求回到“办理中”，B 可以查看原因、补充或修改结果并重新提交；请求重新进入“待发起方验收”，不会因退回而关闭

### 场景 44：退回跨部门协作结果时未填写原因

- **假如** 跨部门协作请求处于“待发起方验收”
- **当** 发起部门经理 A 未填写退回原因就尝试退回
- **那么** 系统阻止操作，请求仍保持“待发起方验收”

### 场景 45：目标部门接受前撤回跨部门请求

- **假如** 一条跨部门请求处于“待对方接受”
- **当** 发起部门经理填写撤回原因并确认撤回
- **那么** 原请求变为“已撤回”，目标部门收到提醒；如仍需协作，发起方可以创建一条新请求

### 场景 46：撤回跨部门请求时未填写原因

- **假如** 一条跨部门请求处于“待对方接受”
- **当** 发起部门经理未填写撤回原因就尝试撤回
- **那么** 系统阻止操作，请求仍保持“待对方接受”

### 场景 47：目标部门接受后尝试取消请求

- **假如** 目标部门经理已接受一条跨部门请求
- **当** 任一方尝试在系统中撤回或取消该请求
- **那么** MVP 拒绝该操作，请求按原目标继续办理

### 场景 48：创始人尝试查看跨部门请求

- **假如** 当前用户是创始人，且存在部门经理之间的跨部门请求
- **当** 创始人打开任务或跨部门协作界面
- **那么** 系统不向创始人展示该请求，也不提供接受、拒绝、验收或协调操作

### 场景 49：执行人尝试撤回待验收任务

- **假如** 执行人已提交任务，任务处于“待验收”状态
- **当** 执行人尝试撤回本次提交
- **那么** MVP 不提供撤回操作；任务保持“待验收”，由验收者验收或填写原因退回

### 场景 50：重新打开已完成任务

- **假如** 一项任务或根任务已完成
- **当** 任何用户尝试将其重新打开为进行中
- **那么** 系统拒绝状态变更；后续工作需创建新的任务

### 场景 51：跨部门请求缺少必填字段

- **假如** 部门经理创建跨部门协作请求
- **当** 请求事项说明或预期交付为空并尝试发送
- **那么** 系统阻止发送并提示补全；期望完成时间、关联任务和附件为空不阻止发送

## 15. 当前待确认事项

本版 MVP 范围内的任务与跨部门协作规则已完成确认，目前没有待确认事项。明确不纳入本版的能力包括待验收提交撤回、独立延期申请、已完成任务重开，以及跨部门请求被接受后的站内撤回或取消。
