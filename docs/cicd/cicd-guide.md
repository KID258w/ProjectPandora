# CI/CD 协作引导

## 当前状态

CI/CD 由负责该模块的组员设计和实现。目前仓库只保留 `deploy/` 占位目录，本项目尚未配置自动检查、镜像构建、镜像仓库或服务器自动部署流程。请不要把本文件中的技术方向理解为已经可运行的部署配置。

## 建议技术方向

- GitHub Actions：运行自动化检查和构建流程。
- Docker Buildx：构建可发布的容器镜像。
- GHCR：存放项目镜像。
- Docker Compose：在服务器上编排 Web 与 Django 服务。
- 云服务器：运行 Docker 服务；云厂商和服务器配置由团队确认后记录。

这是一组建议方向，具体工作流、镜像命名、发布策略和服务器拓扑由 CI/CD 负责人结合项目状态确定，并与统筹人及前后端同学确认。

## CI/CD 负责人待完成

1. 明确开发、测试、发布分支对应的触发规则，以及 PR 必须通过的检查。
2. 与后端、Web 同学确认各自的构建命令、环境变量、静态资源和健康检查方式。
3. 设计 Docker 镜像和 Compose 配置，确保密钥、数据库文件等运行数据不会进入镜像或 Git。
4. 配置镜像发布权限，并在测试环境验证拉取、启动、更新和回滚流程。
5. 确认服务器、域名、HTTPS、防火墙、持久化存储、备份和日志方案。
6. 编写部署操作说明，列出 GitHub Secrets/Environment、首次部署、更新、故障排查和回滚步骤；不得将真实密钥提交到仓库。

## 协作与验收

开始实现前，先通过 Issue 明确负责人、分支名、交付范围和验收条件。完成后提交 PR，至少说明：

- 哪些分支和事件会触发 CI、镜像发布或部署；
- CI 覆盖的检查及本地复现命令；
- 所需 Secrets、权限和服务器前置条件（只写名称与用途，不写密钥值）；
- 验证结果、失败处理、回滚方式及尚未覆盖的风险。

统筹人和相关模块负责人评审后，再按团队分支流程合入。部署到真实服务器前，先在测试环境验证，并确认数据库与上传文件的备份恢复办法。
