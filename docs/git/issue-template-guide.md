# GitHub Issue 提交模板说明

本文用于在 Project Pandora 仓库中创建正式开发任务 Issue。当前文件是团队填写指南和可复制模板；它不会自动显示在 GitHub 的新建 Issue 页面。

## 什么时候提 Issue

需求范围和验收方式已经讨论清楚、准备进入正式开发时，先创建 Issue，再安排负责人和分支。若需求仍有明显疑问，可以先通过讨论或 OpenSpec explore 澄清，不要把未经确认的想法直接写成开发任务。

在仓库的 **Issues → New issue** 中填写标题和正文。创建后记下 Issue 编号，例如 `#123`，用于分支名和 PR 关联。

## 标题建议

使用“类型 + 模块 + 具体目标”的简洁标题，例如：

- `[功能] 任务管理：团队长拆分并派发任务`
- `[缺陷] 日志模块：编辑草稿后内容丢失`
- `[文档] 补充工作视图验收标准`

## 可复制的功能 Issue 模板

```markdown
## 背景与目标
说明为什么要做，以及希望解决什么问题。

## 本次范围
- 要完成：
- 不包含：

## 验收标准
- [ ] 正常场景：
- [ ] 异常或边界场景：

## 关联 OpenSpec
- Change：`<change-name>`
- 相关需求文档：`<docs/requirements/...>`

## 任务分工与分支
| 成员 | 负责内容 | 分支名 |
| --- | --- | --- |
| <成员> | <可独立验收的任务> | `feature/<issue编号>-<简短名称>` |

## 测试要求
- [ ] 单元或组件测试：
- [ ] 集成/手工验证：

## 完成定义
- [ ] 实现符合验收标准
- [ ] 测试结果已记录
- [ ] PR 已通过非作者审阅并合入 `dev`
```

一个 Issue 可以分配给多个成员，各自的任务和分支名应在表格中分别列出。建议在 GitHub 侧栏设置负责人；具体分工以正文表格为准。分支名应唯一，例如 `feature/123-task-api`、`feature/123-task-ui`。

## 缺陷 Issue 补充内容

报告缺陷时，正文还应包含：

```markdown
## 环境
设备/系统/版本：

## 复现步骤
1. <步骤>
2. <步骤>

## 当前结果

## 预期结果

## 附加信息
截图、日志或相关链接（如有）：
```

## Issue 与 PR 的关闭约定

功能 PR 合入 `dev` 时，只写 `关联 Issue：#123`，不要使用 `Closes #123`。Issue 应在相关工作完成并随阶段发布合入默认分支 `main` 后，由 `dev → main` 发布 PR 使用 `Closes #123` 关闭。若一个 Issue 对应多个成员的 PR，不要让第一个功能 PR 提前关闭它。
